# Decisions

This list records owner decisions. The linked documents carry the design and the rationale.

## 2026-10-07: session transport for the guest link and the client link

Entries from this date carry identifiers. The design is in [architecture](arch/index.md), the tests in [test layers](arch/test-layers.md), and the acceptance criteria in [acceptance](acceptance/index.md).

- DC-1: Migration cost is not a selection criterion. The owner asked for the best architecture, because the stack is rebuilt with AI agents at near-zero cost.
- DC-2: Every change ships with unit tests and integration tests. Each integration test runs on the layer that owns the behaviour it checks, because the change spans several layers.
- DC-3: The guest link is built behind one interface with two candidates: a guest helper over one long-lived SSH session, and a guest helper over vsock through Tart's guest agent. One conformance suite tests both. Live test results choose the default.
- DC-4: The cross-layer tests and the shared design live in this repository. mcp-vm-relay keeps its own unit tests and its fake-vm-service tests.
- DC-5: Live tests may upgrade Tart to 2.40.1, run a second vm-service instance on another port with its own state directory, add Tart's guest agent to test image variants, and send commands directly to their own test VMs.
- DC-6: Tests cover both situations: the VM link inside one Mac, and a client link that crosses the internet or an intercontinental intranet. The owner proposed WebSocket with heartbeats for the long-distance link; the design adopts it with a resumable session on top.
- DC-7: The owner leaves the technical choices in this work to the agent. The agent decides, writes the reason into the design, and reports its concerns, their consequences and its actions in plain language.
- DC-8: The finish line comes from measurement, not from the owner: the work is done when the transport is the smallest part of the time between actions. The owner sets no numeric target, because nobody knows this system's limits before it is measured.
- DC-9: Network faults are tested in test VMs with network conditioning, macOS VMs included, with the test plan run by an agent.
- DC-10: The remote session listener may accept clients on other machines, under TLS and a client credential (RS-1).
- DC-11: The mcp-vm-relay changes for the new links are merged once their tests and this repository's live tests pass.
- DC-12: The faster link becomes the default when the measurements support it (DC-3, DC-8).

## 2026-09-29: image resource defaults

- An acquisition that omits CPU or memory gets the image line's configured `CPU` and `MEMORY_MB`, as `vmctl images-show` reports them. The hardcoded 6 CPUs and 16384 MB apply only when the line configures no value. The owner called ignoring the configuration a bug. See [acquisition contract](acquisition-contract.md#acquisition-request-and-compatibility).

## 2026-09-27: lease lifecycle fixes

- (Superseded later the same day.) Execution timeouts are capped at 4200 seconds, which is above the largest request that mcp-vm-relay sends. The owner did not approve this cap.
- A heartbeat without `ttl_hours` renews the lease for its own initial TTL. See [V5](lifecycle-fixes.md#v5-a-heartbeat-without-ttl_hours).
- A heartbeat on a `running` lease whose VM is not running fails, and GC reclaims such a lease after two consecutive passes. See [V2](lifecycle-fixes.md#v2-a-running-record-whose-vm-is-gone).
- At startup the daemon releases `pending` and `provisioning` records left by a previous process. See [V1](lifecycle-fixes.md#v1-startup-reconciliation).
- The daemon releases a new lease whose successful acquisition response cannot be delivered. See [V3](lifecycle-fixes.md#v3-an-acquisition-whose-client-has-gone).
- The 6-hour grace period and the macOS slots held by grace leases are unchanged until the owner decides. See [V6](lifecycle-fixes.md#v6-grace-period-and-macos-capacity-owner-decision-pending).

## 2026-09-27: release preempts guest operations

- Guest execution timeouts have no maximum. The 4200-second cap is removed. See [V4](lifecycle-fixes.md#v4-a-long-guest-operation-blocks-release-and-gc).
- A release preempts a running exec, push, or pull on its VM. The operation is killed and returns an error that says it was cancelled by release. See [V4](lifecycle-fixes.md#design-release-preempts-the-operation-lock).
- GC never blocks on one VM. It defers the teardown of a VM whose operation lock is held and reclaims it on a later pass. See [V4](lifecycle-fixes.md#design-gc-does-not-wait-on-a-busy-vm).

## 2026-10-17: guests that reach the internet only

The design is in [the acquisition contract](acquisition-contract.md#guest-network).

- DC-13: A lease may ask for the network `internet`. Its guest runs on Tart's Softnet, reaches the internet, and reaches neither the host nor any private network. NAT stays the default. The agents that run code in guests through mcp-relay must not reach the host's own services, such as an application's page served on the home network, through a guest. Decided by the agent under DC-7.
- DC-14: An `internet` guest is kept off the host by a stateful host packet filter, a pf anchor that drops the connections a Softnet guest opens to the host's own addresses while replies to the host's own connections pass. The guest uses public DNS resolvers, and every `internet` lease is checked before it is ready: a guest that reaches the host through its gateway fails the acquisition. Stock Softnet passes guest traffic to the host's gateway address, which the live test of DC-13 showed. Decided by the agent under DC-7.
- DC-15: The guest firewall blocks each `internet` guest by its own address, never by subnet. Its anchor holds a pf table of the running `internet` guests' addresses, read from one table file on the host that every vm-service instance writes. vmnet puts NAT and Softnet guests on one subnet when they run together, which the live test of DC-14 showed, so a rule keyed on the subnet cut off NAT guests. NAT guests never enter the table. The isolation check waits for the table to reload. Decided by the agent under DC-7.
- DC-16: `internet` guests resolve names over DNS over TLS to public resolvers, because a host may intercept plain DNS; this host's proxy answers UDP port 53 to any resolver with fake `198.18.0.0/15` addresses, which Softnet drops. Linux guests use systemd-resolved; macOS guests, which offer no scriptable encrypted DNS, run vm-service's own forwarder on `127.0.0.1:53`. The isolation check also requires a name to resolve to a public address and HTTPS to it to work. Decided by the agent under DC-7.

## 2026-10-18: a host whose macOS slots another program holds

- DC-18: When the hypervisor refuses a guest because the number of VMs exceeds the system limit, as its `tart run` log says, the acquisition fails with the capacity refusal, `macOS VM limit reached`, after the usual rollback, so mcp-relay waits for capacity (its DC-22) instead of failing. A macOS image's `acquirable` in `GET /images` also counts the host's Virtualization.framework guests less this service's other active guests. The gauge still never gates an acquisition, because it also counts other programs' Linux guests. On 2026-10-18 another program's macOS guest held a slot, `/images` said `macos26` was acquirable, and the acquisition failed at boot with an error the relay did not wait on. Decided by the agent under DC-7.

## 2026-10-17: a reboot keeps the application catalog

- DC-17: The application catalog compares a base's `st_ino`, `st_size` and `st_mtime_ns` with its association, and no longer its `st_dev`. macOS numbers a volume each time it mounts it, so after the reboots of 2026-10-13 and 2026-10-14 every unchanged base reported a new `st_dev` and `/applications` answered 503 with no usable inventories. Associations still record `st_dev`, so documents that pilot-images writes stay valid. Decided by the agent under DC-7.

- [User] DC-21: The CLI discovers the local instance and every machine-service instance on the intranet through Consul, and it lists every machine from all of them. See [FD](arch/federation.md) and [CL](ux/cli/index.md).
- [User] DC-22: An instance exposes the Mac it runs on as a durable machine, never called "bare metal" or a "physical machine", because the instance on it is durable. - [User] DC-23: A session on a durable machine runs as the existing admin account, `wezzard`, not as a non-admin evaluator account. - [User] DC-24: Claude Code and Codex on a durable machine use the in-house LiteLLM gateway with a stable key per machine per agent, so that usage is tracked per machine. Claude Code uses `ANTHROPIC_BASE_URL` set to the gateway and `ANTHROPIC_API_KEY` set to a key that the gateway accepts, from `~/.config/machine-service/agents/claude-code.env`. The directory is mode 700 and the files are mode 600. The service loads the keys into a session's environment and never prints, logs or returns them. (Where the base URLs come from is superseded by DC-32.) See [AK](arch/agent-keys.md).
- [User] DC-25: The CI runner is not paused. The readycheck-dev GitHub Actions runner on 192.0.2.4 and 192.0.2.5 runs as the operator's account, and leases coexist with its jobs. See [HY-5](arch/hygiene.md#hy-5-the-lab-runners-hold-the-lease). (Superseded on these Macs by DC-1xx-LAB-2: a lab job holds the lease.)
- [Agent] DC-26: A durable machine admits one lease at a time. The rule holds across every instance on one Mac, so a second instance for tests cannot lease the same Mac twice. See [DM-2](arch/durable-machine.md#dm-2-one-lease-at-a-time).
- [Agent] DC-27: A durable machine reports the same fields as a virtual machine, plus hardware facts: chip, memory, free disk, GPU and Metal family, and installed engines. Consumers choose a machine by capability. For example, an Unreal post-process evaluation needs Metal 3, which a Tart VM lacks: its paravirtual GPU was measured to support only the `mac2` and `common3` families, no `metal3`, and argument buffers tier 1. See [MM-3](arch/machines.md#mm-3-capability-report).
- [Agent] DC-28: Hygiene on each durable lease is a scratch workspace, a sweep of leftover processes, and an inventory before and after the lease that is recorded with the lease. Hygiene reports what it finds and never refuses a lease. See [HY](arch/hygiene.md).
- [Agent] DC-29: A command on a durable machine runs as a child of the machine-service LaunchAgent in `wezzard`'s logged-in GUI session, not over SSH. The service has no SSH hop to itself, and macOS attributes privacy permissions (TCC) to the service's own signed executable, which the owner grants once. See [DM-4](arch/durable-machine.md#dm-4-exec).
- [Agent] DC-30: A client acquires and works on a machine through the instance that owns it. Instances never call one another, and no instance schedules work onto another Mac. Push and pull to a remote instance carry the file bytes in the request, because a host path on the client's Mac means nothing on the instance's Mac. See [FD-4](arch/federation.md#fd-4-working-on-a-remote-instance).
- [Agent] DC-31: (Superseded by DC-33 and DC-37.) The rename keeps every current name working for a compatibility window that closes when mcp-relay and the evaluation runner use only the new names.
- [User] DC-32: No in-house endpoint appears in this repository. The gateway base URLs that Claude Code and Codex use are local configuration injected into a machine. They are never part of a VM image or a durable machine's software baseline, and never a default in code or documents. On a durable machine the operator configures them once, in a local file beside the key files. On a virtual machine they are injected at lease time from host-local configuration, like a credential pack. Documents name them only abstractly, with placeholders such as `http://<gateway-host>`. This supersedes the base-URL part of DC-24. See [AK-2](arch/agent-keys.md#ak-2-gateway-endpoints-are-local-configuration).
- [User] DC-33: The rename, mcp-relay's switch to the new names and API, and the evaluation runner's switch land together in one coordinated milestone. There is no long compatibility window. This supersedes DC-31. See [MG-3](arch/rename.md#mg-3-one-coordinated-switch).
- [User] DC-34: The image list reloads without a restart. Adding, updating or removing an image line, a host-local base association or a promoted base changes the available virtual machines without restarting the daemon. A failed rebuild keeps serving the last good list and reports the failure loudly, no partial list is ever published, and the existing trust rules for executing `line.conf` still hold. See [IC](arch/image-catalog.md).
- [User] DC-35: The CLI is renamed `machctl`. The service stays machine-service. The name is close to systemd's `machinectl` on purpose, and macOS has no `machinectl`. This supersedes the CLI's name in DC-19. See [MG-1](arch/rename.md#mg-1-names).

The old paths answer HTTP 410 Gone with the new path in the error, the daemon refuses to start when it finds a `VM_SERVICE_*` variable, and no `vmctl` link is installed. ## 2026-10-21: the durable lease in M1

- [Agent] DC-48: macOS 27 does not let a process read another process's start-up environment: `KERN_PROCARGS2` answers the arguments only, and `ps eww` shows no variables. HY-3's environment rule therefore finds nothing there. The sweep keeps the rule for systems that answer, and classifies one process snapshot before it sends any signal, so a child that left a lease session while its parent still ran is ended as a descendant. A process that left the lease's sessions after its parents exited survives a release on macOS 27. Found by the component tests on 192.0.2.3. See [HY-3](arch/hygiene.md#hy-3-leftover-process-sweep).
- [Agent] DC-49: Component tests move the host-wide lease lock to their own folder with `MACHINE_SERVICE_DURABLE_LOCK_DIR`, which only debug builds honour. A release build refuses to start while it is set, so every installed instance shares the lock in `/var/tmp`. Live tests (TL-6) never set it. See [DM-2](arch/durable-machine.md#dm-2-one-lease-at-a-time).
- [Agent] DC-50: Until the byte-carrying transfers of FD-4 exist, path-based push and pull on a durable machine answer 409 for a client that is not on loopback, because its paths mean nothing on the instance's Mac. A transfer from or into the agent key folder is refused, so no transfer copies a key into a file (AK-5). See [DM-5](arch/durable-machine.md#dm-5-push-and-pull).
- [Agent] DC-51: A session's `CODEX_HOME` is always the workspace's `codex/` folder, as DM-1 says, and `config.toml` is written only when Codex is loaded. A session without Codex loaded therefore never touches `~/.codex` either. See [AK-4](arch/agent-keys.md#ak-4-codex).
- [Agent] DC-52: The Homebrew formulae and the casks are two inventory parts. On 192.0.2.3 `brew list --cask` fails on an untrusted tap, and as one part it hid the formulae as well. See [HY-4](arch/hygiene.md#hy-4-inventory-before-and-after).
- [Agent] DC-60: `machine-service-install catalog-description` describes the instance as installed, not the operator's shell. Exposure comes from `--expose-durable`, else the installed LaunchAgent's `MACHINE_SERVICE_EXPOSE_DURABLE`, else off, and any other value is refused so that a typo never adds or drops the `durable` tag. The virtual-machine check runs against the installed agent's environment, with the daemon's own strict image-catalog build and `tart list`, so the check and the catalog the daemon serves cannot disagree. `disposable-infra` stays with `vm` and `tart`, because it describes the disposable clones. `install --expose-durable on|off` writes the variable, and later installations preserve it like every installed value. See [FD-1](arch/federation.md#fd-1-registration).
- [Agent] DC-61: (How a registration's ID is known, and the local ID's fallback, are corrected by DC-80.) The local instance and a Consul registration are the same instance when their instance IDs and their ports match. A registration's ID is the `instance` it states in its metadata, else its node name. The local ID is the `instance` of its `/health`, else the Mac's local host name. Two instances with one ID are named `<id>:<port>`. A second instance for tests runs on the same Mac under the same ID (TL-4, TL-6), and matching by ID alone would hide the installed instance behind it. See [FD-2](arch/federation.md#fd-2-discovery).
- [Agent] DC-62: The Consul agent gets 5 seconds, and each instance gets one 5-second budget for every request the CLI sends it. All instances are asked at once, so a list takes at most about 10 seconds whatever is down. The requests ignore proxy variables and follow no redirect. A registration that the registrar published as `loopback_only` on another node is shown as unreachable without a request, because its address would be the asker's own loopback. A Consul agent that does not answer is named on standard error, and the local instance is still listed. See [FD-3](arch/federation.md#fd-3-aggregation).
- [Agent] DC-63: `machctl list --json` prints a JSON array with one object per instance. Besides CL-1's fields, each object has `local`, `consul` (its health) and `catalog`. A reachable instance with no machine shows one `none` row, so that it is never missing from the table, and the row is dropped while a filter is active. The command exits 0 when any instance answered and 2, with the start hint, when none did. A required capability over an unknown fact never matches. `claude-code` and `codex` need the program and, where the record reports agent keys, a present key and endpoint. `ci-idle` matches a Mac without a CI runner or with an idle one. See [CL-1](ux/cli/list.md#cl-1-the-machine-list) and [CL-2](ux/cli/list.md#cl-2-acquire-by-capability).
- [Agent] DC-64: `status`, `heartbeat`, `release`, `wait`, `exec`, `push` and `pull` find their machine's instance from the merged list. A name that no instance lists goes to the local instance, whose own answer then says it is unknown. The console commands stay with the local instance, because their viewer runs on the service host. Push and pull by host path are refused for a machine on another instance until the byte-carrying endpoints of FD-4 exist, since a host path means nothing on another Mac. A selected environment never discovers other instances and refuses `<vm>@<instance>`, because its fingerprint belongs to its own instance (CN-1). See [CL-3](ux/cli/list.md#cl-3-naming-a-machine).

## 2026-10-21: M2, the service side

- [Agent] DC-65: A Mac without Tart installs as a durable machine only. The installer always requires `machine-service` and `machctl` beside it, and requires the virtual-machine helpers (`console-worker` and both guest console agents) and checks Tart's version only when Tart is found (`TART`, else `tart` on the installed agent's `PATH`). Without Tart and with durable exposure off the installation is refused, because the instance would offer nothing, and the refusal names both settings. See [MG-4](arch/rename.md#mg-4-order-of-migration) and AC-38.
- [Agent] DC-66: The `virtual` kind of `/health` needs Tart as well as an available image catalog. On a Mac without Tart, `GET /machines` lists no offer and says why in `offers_unavailable`, and an image acquisition answers 400 `this instance cannot create virtual machines: <reason>` before anything is reserved. See [MM-1](arch/machines.md#mm-1-two-kinds-of-machine) and AC-38.
- [Agent] DC-67: An offer is one record per image of the current catalog under `offers` in `GET /machines`, with `name` and `image` both the image, `kind: "virtual"`, `state: "offer"`, `image_kind`, `base_vm`, `base_available`, `defaults` and the `concurrency` figures of `GET /images`. Its capability report has the durable report's sections with `source: "image"` and `network: "nat"`: `os.name` from the line's kind with no version, `hardware` and `disk` from the line's defaults, the measured paravirtual GPU for macOS and no Metal device for Linux, `software` from the image's validated application inventory, and `display`, `permissions`, `agents` and `ci_runner` unknown with their reason. A running virtual machine's record carries its image's report. `tart` in `software` is Tart itself, never `tart-guest-agent`. See [MM-3](arch/machines.md#mm-3-capability-report).
- [Agent] DC-68: An unavailable durable machine refuses an acquisition with 409 `durable machine unavailable: <name> (<reason>)`, after the request's own validation, so that the CLI treats it as a capacity refusal and tries the next candidate. A console that could not be read never makes the machine unavailable, and a lease that exists keeps its state. See [MM-5](arch/machines.md#mm-5-states).
- [Agent] DC-69: `machctl acquire` has three exclusive forms, `--image` (the default, `macos26`, optionally with `--instance`), `--machine` and `--require`, and refuses the virtual-machine-only flags with the two durable-capable forms. The `chose <name> (<why>)` line goes to standard error before each attempt, so standard output stays the lease's JSON. Only `durable machine leased`, `durable machine unavailable` and `macOS VM limit reached`, each with 409, pass to the next candidate; any other refusal ends the command. See [CL-2](ux/cli/list.md#cl-2-acquire-by-capability).
- [Agent] DC-70: The byte-carrying endpoints stage the body under `<state>/transfers/<id>/`, check the machine and the durable lease before keeping a byte, refuse a digest mismatch with 400, and then run the instance's own path transfer on the staged path, so every rule of a path transfer still applies. Path-based push and pull of a virtual machine now serve loopback clients only, as DC-50 made them for the durable machine, because from another Mac a host path would name the service host's own files. This supersedes the push and pull refusal of DC-64. See [FD-4](arch/federation.md#fd-4-working-on-a-remote-instance).
- [Agent] DC-71: The wire form lives in one crate, `byte-transfer`, shared by the instance and `machctl`. A folder travels as a tar stream of its contents, regular files and folders only, with their modes; a stream that names an absolute path, a `..` component, a link or a device is refused whole and nothing is unpacked. `X-Content-SHA256` is the lowercase hex SHA-256 of the body itself. `GET` names the item in `X-Content-Name`. See [FD-4](arch/federation.md#fd-4-working-on-a-remote-instance).
- [Agent] DC-72: `cli-leases.json` lives in `$MACHINE_SERVICE_STATE`, else `~/.local/state/machine-service/`, holds `{schema_version: 1, leases: [{machine, instance, lease_id}]}` with the owning instance's address, and is written with mode 600 under an exclusive `flock` on a sibling lock file and replaced by a rename. A lease is found by machine and address, or by machine alone when only one is remembered. ## 2026-11-02: the remote session library

- [Agent] DC-108: The `remote-session` crate is blocking, like the rest of the workspace: `tungstenite` 0.30 over `rustls` 0.23 with the `ring` provider, which needs no C toolchain to cross-build the relay agent for Linux. A WebSocket over TLS cannot be read and written from two threads, so one thread per connection alternates: it writes what the session has, then reads with a 10 ms socket timeout. A send waits at most that long before it goes out. See [RS-1](arch/remote-session.md#rs-1-transport).
- [Agent] DC-109: Control messages (`hello`, `welcome`, `expired`, `error`, `ack`, `bye`) are JSON text messages tagged by `type`; the hello also carries `version: 1` and opaque `attributes`, such as BK-1's role. An envelope is a binary message: `seq` and `ack` as big-endian `u64`, then the opaque body, so a body needs no encoding and the 1 MiB cap of TC-8 is a byte count. A body is at most 1 MiB − 16 bytes: `send` refuses a larger one with `TooLarge`, `split_body` cuts a payload into bodies, reassembly belongs to the payload layer, and a WebSocket message or frame over 1 MiB is refused on receipt. See [RS-2](arch/remote-session.md#rs-2-session-sequence-and-acknowledgement) and [TC-8](arch/transport-contract.md#tc-8-a-message-may-be-limited-in-size).
- [Agent] DC-110: The heartbeat is the protocol's own `ack` message, not a WebSocket ping as RS-4 says. A proxy that ends TLS may answer pings itself, so a pong would show only that the hop to the proxy is alive. Each side sends an `ack` after 5 s without sending (at most 30 s is accepted, TC-3) and drops a connection after 15 s without receiving. A connection is also dropped when bodies written on it wait 15 s for an acknowledgement that does not advance, because the peer acknowledges on receipt: the TL-1 simulation found that a body lost on a live connection with nothing sent after it would otherwise never be resent. See [RS-4](arch/remote-session.md#rs-4-heartbeat-and-dead-connection-detection).
- [Agent] DC-111: Reconnect backoff doubles a base from 250 ms up to 5 s and waits a uniform delay between half the base and the base, so the wait never exceeds 5 s. The client resolves the broker's host name again on each attempt (TC-4, TC-6). After the welcome's `grace_ms` plus its own dead-connection bound without a resume, the client ends the session as expired with reason `grace_elapsed` without waiting for a server to say so, because the server notices a loss at most that much later than the client and has dropped the session by then. See [RS-4](arch/remote-session.md#rs-4-heartbeat-and-dead-connection-detection) and [RS-5](arch/remote-session.md#rs-5-grace-period).
- [Agent] DC-112: Sessions live in memory. A resume of a session the server dropped at its grace period is answered `expired` with reason `expired`, which the server remembers for 1 hour; a session it has no record of, such as one from before a restart, is answered with reason `unknown`. A server that shuts down drops its connections without a `bye`, as a crash would. All three reasons mean the same thing to the payload layer: start a new session and query the execution IDs that were in flight (RS-3). A side that closes while disconnected ends alone; its peer ends at the grace period. See [RS-5](arch/remote-session.md#rs-5-grace-period).
- [Agent] DC-113: The server's authenticator sees the hello's bearer credential, its attributes and the peer address, and runs on every hello, resumes included. It names a principal, and a session resumes only for the principal that opened it, otherwise the answer is `error` with code `forbidden`. Session IDs are random UUIDs. The other refusal codes are `unauthorized`, `protocol` and `unsupported_version`. No client certificate is asked for (TC-5). See [BK-2](arch/broker.md#bk-2-pairing-and-routing).
- [Agent] DC-114: A client trusts the Mozilla roots (`webpki-roots`) and the PEM roots its caller adds, such as a lab's own authority, and not the system store, so it behaves the same on macOS and Linux and inside a LaunchAgent. Both sides offer only ALPN `http/1.1`, so a proxy that ends TLS does not choose HTTP/2 towards either side. Plain `ws://` is allowed only when every address of the host is a loopback address, and a server without TLS accepts connections only on loopback. See [TC-1](arch/transport-contract.md#tc-1-one-outgoing-websocket-over-tls) and [RS-1](arch/remote-session.md#rs-1-transport).
- [Agent] DC-115: The server is mounted in one of two ways: `SessionServer::listen` on a listener of its own, or `SessionServer::handle_connection` for each connection that machine-service's session listener (`MACHINE_SERVICE_SESSION_PORT`) accepts. Either way it serves TLS and the WebSocket upgrade at its configured path, `/relay` by default (BK-1), and answers other paths with 404. machine-service does not mount it yet. See [BK-1](arch/broker.md#bk-1-endpoint).
- [Agent] DC-116: `send` waits while the session holds more than 64 MiB unacknowledged (configurable), and `try_send` fails instead. A receiver acknowledges a body when it reaches the session's inbox, not when the payload layer takes it, so the inbox itself has no bound; the payload layer is expected to keep reading.
## 2026-11-02: the relay agent core

- [Agent] DC-117: The guest session agent and the relay agent share one crate, `guest-actions`, which holds the shell, process-group, atomic-write and read rules of GS-3. The relay agent uses it instead of a copy, so the two agents cannot drift apart ([RA-9](arch/relay-agent.md#ra-9-relation-to-the-guest-session)).
- [Agent] DC-118: Losing a link does not stop a command. The relay agent kills the process groups of running commands only when it stops: on a stop signal, at the end of its `stdio` input, or at shutdown. A session can end and resume while a command runs, and the outcome waits in the record ([RA-3](arch/relay-agent.md#ra-3-the-relay-agent-dials-out)).
- [Agent] DC-119: `exec`, `script` and `write` commit at their end message, after the uploaded bytes match it. `read`, `cancel` and `status` commit when they arrive. The record reaches the disk before the operation takes effect. A failure before the commit point is answered with `committed: false` and is not recorded, so the client may send the same execution ID again.
- [Agent] DC-120: The agent writes a command's combined output into the execution's record, and a repeated execution ID replays the output from its first byte, then follows the command while it runs. A read's bytes are not kept: a repeated read ID returns the recorded size and SHA-256 without the bytes. A read has no effect in the guest, so a client reads again under a new execution ID ([GS-5](arch/guest-session.md#gs-5-failure-outcomes-at-most-once)).
- [Agent] DC-121: Records live in `~/.local/state/relay-agent/executions/<SHA-256 of the ID>/` and are kept for 24 hours, longer than the broker's hour ([RS-3](arch/remote-session.md#rs-3-operations-and-execution-ids)). A record that a crashed agent left running opens as `interrupted` and never runs again. Hashing the ID makes every ID a safe directory name.
- [Agent] DC-122: A chunk is binary: the byte `0x01`, the 8-byte call number, and at most 1 MiB less 4 KiB of data, which leaves room for a session envelope under TC-8's 1 MiB. Every other message is JSON with external enum tags, because the workspace's `serde_json` `arbitrary_precision` feature breaks numbers inside internally tagged enums.
- [Agent] DC-123: An end message names its execution ID as well as its call number. The randomized test found that a broker that reuses a call number could otherwise get another call's chunks and end to commit a pending upload with the wrong bytes.
- [Agent] DC-124: `cancel` and `status` are operations with their own execution IDs, recorded like the others, not separate message types. The agent sends a heartbeat every 10 seconds, under TC-3's 30.
- [Agent] DC-125: The agent catches its stop signals with a handler that writes to a pipe, instead of blocking them. A blocked signal stays blocked in the commands the agent starts, and the TL-2 test showed a command that could not be stopped by `SIGTERM`. A caught signal returns to its default action at `exec`.
- [Agent] DC-126: The agent uses `~/.config/relay-agent/config.json` only when it is a regular file owned by the agent's user with mode exactly 600, checked on the opened file. Until then it checks every second and logs each new reason once. The file holds `broker_url` (`ws://` or `wss://`) and `agent_credential` (pilot-images RA-I2, RA-I3).
- [Agent] DC-127: The transport is a trait for an ordered, reliable, message-oriented duplex link with opaque payloads. The agent core holds no WebSocket, TLS or resume code. `relay-agent stdio` serves one link of length-prefixed messages on standard input and output, for the TL-2 tests and local use. `relay-agent run` waits for its configuration and serves the links that an injected dialer opens, with backoff from 250 ms to 5 s and jitter. The resumable WebSocket session will supply that dialer.

## 2026-11-03: resumable streams (relay protocol 2)

- [Agent] DC-195: An upload is a stream with a resumable offset, not a blob the broker buffers. The relay agent writes it into a spool named by the execution ID (the hidden sibling of a file's destination, the tar spool beside a folder, or a command's standard input in its state folder) and keeps it across lost sessions and its own restarts; after any loss the sender asks for the agent's committed offset and continues there. The SHA-256 of the whole stream and the rename at the end stay the commit point, so a stream is at most once and never visible half written. The broker passes the stream through and holds about one window of it. This replaces DC-145's whole-upload buffering and lifts the 256 MiB bound of RP-5 and DC-170, which made AC-58's 2 GB push impossible and tied the broker's memory to the file's size ([RP-15](arch/relay-protocol.md#rp-15-resumable-streams)).
- [Agent] DC-196: Flow control lives in the relay protocol, end to end, not in the session: the receiver reports `progress {call, execution, committed}` when it takes a call and at least every 4 MiB, and a sender keeps at most 32 MiB beyond the last one. The session's inbox takes whatever arrives and its acknowledgements say nothing about what the payload layer consumed, and another change is reworking the session's flow control and acknowledgements; a window counted in the payload's own bytes bounds the broker whatever the session does. The broker enforces it: a client that sends more is refused with `window_exceeded` before it can fill the broker. 32 MiB keeps a 1-second round trip (TC-7) above 30 MiB/s; 4 MiB keeps eight reports in flight within it.
- [Agent] DC-197: A sender continues with the same `call` and `"resume": true`; the agent's first answer is `progress` with its committed offset, and the chunks that follow start there. Chunks keep protocol 1's binary form without an offset field, because only one call of an execution ID feeds its upload at a time (a later one supersedes it), so the agent always knows where the next chunk goes. A `call` without `resume` starts the upload again, so a client that does not know about a held upload never continues stale bytes.
- [Agent] DC-198: When the relay agent's session ends during a client's upload, the broker answers the call `upload_incomplete` (not committed) at once instead of waiting for the agent's next session: it holds none of the lost bytes, and the client's resumed call waits for the agent itself (RP-8). An upload whose `end` had reached the broker is sent again with `resume` and its `end` and no chunks; the agent commits it when it holds every byte, replays it when it had committed, and answers `upload_incomplete` otherwise. An upload the broker reads itself (machine-service's own push, a new relay agent build, the bootstrap probe) continues on its own from the agent's committed offset. A client whose session ends before its upload's end leaves the agent's spool for its next session, and the broker forgets the call's record at once, so the resumed call does not attach to a failed record.
- [Agent] DC-199: `progress` counts the bytes the agent wrote, not the bytes it flushed; the agent flushes the spool and writes its record (not itself flushed) every 64 MiB, when the link that feeds it ends, and before it stops or restarts. Within one agent process written bytes are as good as flushed ones, and a resumed call asks again, so a sender never relies on an old report. An agent that restarts reopens each spool at its record's committed offset, drops what follows and hashes the kept bytes again, so the SHA-256 still covers the whole stream. Flushing every 4 MiB would cost 500 full flushes on a 2 GB push on macOS, where Rust's flush is `F_FULLFSYNC`.
- [Agent] DC-200: The agent's own streams are resumable too: a `call` may name an `offset` at which a read, a folder read or an exec's replayed output starts, and the `end` still names the whole stream. A client continues a read it lost under a new execution ID (a read's bytes are not recorded, DC-120) with the bytes it holds as the offset; the broker continues one across a lost agent session with the bytes it delivered. The broker acknowledges the agent's streams as the client's session takes them, and the agent sends at most the window beyond, so a slow client no longer piles the agent's output into the broker. A folder's tar stream is made in sorted order (DC-169), so it continues at an offset while the folder does not change, and its whole SHA-256 catches a change.
- [Agent] DC-201: The relay protocol becomes 2 and is negotiated with the existing fields: the agent's `hello.protocol`, the broker's `ready.protocol`, which the broker now also sends to each agent right after its hello, and a client's `attributes.protocol` in its session hello. Each side speaks the lower version. A client of protocol 1 keeps the old path, an upload held whole up to 256 MiB; an agent of protocol 1, as an image may ship before machine-service replaces it (RA-6), gets no protocol-2 field or message, and the broker reports progress for it as it passes the bytes on. A protocol-2 agent behind a protocol-1 broker never hears `ready` with 2 and behaves as before.
- [Agent] DC-202: A held upload is dropped when a `cancel` names it (`discarded`), when a purge removes its lease's records, when a call without `resume` starts it again, and 24 hours after its last byte. A restart of the agent (RA-6) does not wait for held uploads, because their spools survive it; the broker only restarts an agent while no call of the lease is out.
- [Agent] DC-203: A chunk or `end` for a call that is not open is dropped instead of closing the client's session: with resumable uploads a call ends with `upload_incomplete`, `window_exceeded` or a replayed result while the client's chunks for it are still on the way. A body that is not a relay message is still a protocol error.
- [Agent] DC-204: A command's standard input and a script are spooled like a file and fed to the command from the spool at its start, so neither is bounded by the agent's memory; the agent's 256 MiB `MAX_UPLOAD` is gone.
- [Agent] DC-205: machine-service's own push and pull on a `relay` lease stream through files: a pushed file is read from the disk at any offset, a pushed folder's tar stream is spooled to a temporary file, and a pull streams into a temporary sibling that is renamed into place once its bytes match. A transfer's bound is five minutes plus a second per MiB, so a 2 GB transfer over a slow link is not cut at 300 seconds. The durable relay route does the same.
- [Agent] DC-206: AC-58's 10,000-file tree never ran: the check was hard-coded `blocked` with the M3c reason ("a folder moves by scp on a relay lease, DC-151"), which went stale when write_tree and read_tree landed (DC-169), so every run reported it blocked and none tried it. The scenario now pushes the tree as one write_tree stream, compares the guest's sorted file list and contents by SHA-256 with the client's, reads it back with read_tree and compares again. Its 2 GB push streams with `resume`, so the check no longer waits on large uploads (DC-187).
- [Agent] DC-207: TL-2 proves the memory bound with a 3 GB synthetic stream uploaded and read back through a broker whose sessions hold at most 8 MiB unacknowledged, in a test binary of its own: the broker reports the most stream bytes it ever held (`held_most`), which must stay within one window and two chunks, and the process's peak memory, which holds the client, the broker and the agent, must stay under 768 MiB. ## 2026-11-03: flow control on a healthy slow link

- [Agent] DC-208: The reconnects about every 15 s under N2 and N3 came from the remote session itself, not the network. An in-process session pulling over the rig's N2 chain, with no scheduled fault, lost its connection 4 times in 600 MiB: the sender, with up to its whole 64 MiB replay buffer in flight, filled the path's queues with 16 s of data at 4 MB/s, and the rig's edge, which handles a connection's messages in order, held the receiver's acknowledgements and heartbeats behind those bytes for up to 10 s, then let them go in a burst. The sender then saw neither traffic nor progress for 15 s and dropped a healthy link, and each resume sent the in-flight bytes again. A 6 MiB bound on the same run made the reconnects disappear. A 2 GB pull through the rig under N2 (`flow_rig`) took 932.8 s with 14 reconnects before the change and 547.3 s with none after it. Liveness stays judged by progress (an acknowledgement that advances while bodies are in flight, DC-110), and a connection now holds only an in-flight window of unacknowledged bytes, so that progress is visible on any healthy link. See [RS-4](arch/remote-session.md#rs-4-heartbeat-and-dead-connection-detection).
- [Agent] DC-209: The in-flight window adapts to measured throughput rather than being fixed: the bytes acknowledged per second over the last 10 s of busy time, times the smallest round trip plus a third of the dead-connection bound (5 s), from 1 MiB up to the replay buffer, starting at 4 MiB on each connection. A fixed window cannot serve both ends: 6 MiB moved N2 at 2.66 MB/s, below its bandwidth-delay product, and anything large enough for a fast link floods a slow one. The throughput is an average, not the best of short samples, because a short sample read up to 25 MB/s on the 4 MB/s link when held acknowledgements arrived in a burst, and the window sized from it grew back to 64 MiB. The round-trip term keeps the window growing while the link has room; without it, `rate × 5 s` only sustained the rate it had, 3.40 MB/s on N2. The queue a side builds drains within 5 s, a third of the bound; on N2 the longest silence the sender saw fell from more than 15 s to 7 s. The replay buffer's 64 MiB (DC-116) is unchanged. The wire is unchanged, so either side may run either rule against the other. See [RP-2](arch/relay-protocol.md#rp-2-the-session).
- [Agent] DC-210: Each side acknowledges a body on receipt, in the next envelope or at once in an `ack` message, and nothing waits for an acknowledgement before sending on, so an action costs one round trip of the open session (DC-194). The session counts its connections, bodies sent and received, flights (runs of sends with nothing received between them) and round trips from an envelope's write to the acknowledgement that covers it (`Session::counters`). An action's round trips are its flights plus its new connections. AC-70 fails when any of its 100 actions costs other than one, and reports the path's round trip from the call's envelope to the broker's acknowledgement beside the link and guest times; a broker test checks the same on the in-process broker and agent. See [AC-70](acceptance/relay.acceptance).
- [Agent] DC-211: The TL-2 fault proxy can cap bandwidth and carry both directions of a connection through one queue, the property of the rig's edge that turned a full window into a stall. A 48 MiB transfer at 8 MB/s with a 1.5 s bound reconnects without the window and never with it, and a hang in the middle of the same transfer is detected within the bound and resumed with each body once. `relay-acceptance`'s opt-in `flow_rig` test runs a bulk transfer through the real rig under any profile and reports its reconnects and throughput.
- [Agent] DC-212: A link slower than about 70 KB/s cannot carry one 1 MiB envelope within the 15 s bound, whatever the window, because progress is counted in whole bodies. That is below TC-7's links and below every profile, so it is left as it is; byte-level progress in the acknowledgement would be the change if such a link is ever served.
