# Installation (IN)

## Why

- The daemon finds its helpers beside its own executable, and nothing kept the folder it runs from complete. The executables were copied by a hand-kept list in the README, and the installer checked a second hand-kept list. Neither named `guest-session-agent`, so on the installed service every exec, push and pull over the session link failed with `guest session agent unavailable at …/guest-session-agent` (DC-79).
- An installation is correct only when it holds every executable the daemon looks up. Two lists can disagree; one list cannot.

## IN-1: One layout

- The `service-layout` crate is the one list of the executables an installation places beside the daemon, with when each is needed and which guest kinds need a build of their own.

| Executable | Needed | Guest builds |
| --- | --- | --- |
| `machine-service` | always | |
| `machctl` | always | |
| `machine-service-install` | always | |
| `console-worker` | with Tart | |
| `guest-console-agent` | with Tart | `-linux` |
| `guest-session-agent` | with Tart | `-linux` |
| `vm-service-dot-forwarder` | with Tart | |
| `vm-service-guest-firewall` | with Tart | |

- The relay agent is not an executable of this list. The installation holds its published release instead, the folder `relay-agent-release/`: the archives `relay-agent-<version>-<platform>.tar.gz` and `SHA256SUMS`, exactly as `rust/scripts/build-relay-agent.sh` and the release workflow make them (DC-140). It needs the `darwin-<arch>` archive with Tart or with durable exposure on, and the `linux-<arch>` archive with Tart, on the host's own architecture.
- A guest agent runs inside the guest as machine code. The host-native build serves macOS guests, and Linux guests need the `-linux` build. A kind-qualified file beside the daemon, `<name>-<kind>`, outranks the host-native one.
- The daemon resolves every helper through this crate: the console worker, both guest agents, the release whose relay agent it uploads into a clone ([RA-7](relay-agent.md#ra-7-bootstrap)), the forwarder and the firewall installer it names in its fixes. A helper is an entry of the layout or it cannot be resolved.
- The installer requires the same list, so it can neither miss an executable the daemon looks up nor require one it never uses. A Mac without Tart needs the first three only (MG-4 step 5, DC-65).
- The override variables `VM_GUEST_SESSION_AGENT`, `VM_GUEST_CONSOLE_AGENT`, `VM_CONSOLE_WORKER` and `MACHINE_SERVICE_DOT_FORWARDER` still win over the layout. `MACHINE_SERVICE_RELAY_AGENT_RELEASE` names another release folder of the same form; no variable names a relay agent executable.

## IN-2: Install into a folder

- `rust/scripts/build-release.sh` builds every executable in the release profile and puts each under its installed name in `target/machine-service/`, and makes the relay agent's release there with `build-relay-agent.sh` for the platforms the layout names.
- `machine-service-install install --prefix DIR`, run from that folder, checks that every executable of the layout is beside it, then, after the old job has stopped, copies exactly those executables into `DIR`, each through a temporary file and a rename with mode `0755`. The LaunchAgent runs `DIR/machine-service`, and `~/.local/bin/machctl` links to `DIR/machctl`.
- A missing or non-executable file refuses the installation by name before anything is copied, written or loaded. Nothing else in the build folder is copied.
- The release is checked before anything is written: every archive matches `SHA256SUMS`, each needed platform has an archive holding the one file `relay-agent`, and on an exposed Mac the macOS executable is signed with the identifier `com.wezzard.relay-agent` (DC-135): with Developer ID by the team the instance trusts (IN-3), or, for a pre-release only, ad hoc (DC-224), and it does not downgrade the signing of the agent in place (DC-232). A `SIGNING.json` that disagrees with the executable is refused, and the installer prints which signature it found and how its team is trusted ([signing](../signing.md)). The daemon runs the same trust check on the release it holds, at startup and before every upload or replacement, so an instance whose installation did not check it, such as a Tart-only one with exposure off, is held to it too ([RA-6](relay-agent.md#ra-6-delivery-and-update), DC-236). It is copied verbatim through a temporary folder that replaces the old one. The `relay-agent` and `relay-agent-linux` files of the earlier layout are removed.
- Without `--prefix`, the folder beside the installer is the install folder, as before. `--check` with `--prefix` checks the build and writes nothing. `--prefix` with `remove` is refused.
- Every other rule of an installation still holds: it refuses while any lease record exists, and it keeps the installed environment.

## IN-3: The durable Mac's relay agent

- Every instance with durable exposure on has one relay agent of its own, and the instance's state folder names it, so no two instances on a Mac share a label, a configuration, an executable or execution records (DC-213):
  - The instance on the default state folder, `~/.local/state/machine-service`, is the installed one. Its agent is the LaunchAgent `com.wezzard.relay-agent` under the operator's home: the executable at `~/.local/libexec/relay-agent/relay-agent`, as in every guest, the configuration `~/.config/relay-agent/config.json` and the LaunchAgent `~/Library/LaunchAgents/com.wezzard.relay-agent.plist`, which launchd loads at every login.
  - Any other instance's agent is `com.wezzard.relay-agent.<the first 12 hex digits of the SHA-256 of its state folder>`, with every file of it, its LaunchAgent included, under its root `<state>/relay/agent/`, which the agent is told as `RELAY_AGENT_ROOT`; its `HOME` stays the operator's, because its commands are the operator's session's ([DM-1](durable-machine.md#dm-1-a-lease-is-a-session-and-a-workspace)). That LaunchAgent is outside `~/Library/LaunchAgents`, so launchd runs the agent only while its instance has loaded it and never at a later login, and removing the state folder removes all of it.
- Each agent has the per-machine agent credential `<state>/relay/durable-agent.credential` and the broker's authority `<state>/relay/tls/` of its instance, made when missing, and a configuration (mode 600) with `broker_url` `wss://localhost:<session port>/relay`, the credential and the authority. Its LaunchAgent has `LimitLoadToSessionType` `Aqua`, `RunAtLoad`, `KeepAlive`, `HOME` set to the operator's home, `PATH` set to the operator's login shell's (`zsh -l`), as a terminal of the desktop session has it, and, for a second instance's agent, `RELAY_AGENT_ROOT`, and is bootstrapped into `gui/<uid>`; without a desktop session it is refused ([RA-2](relay-agent.md#ra-2-where-the-relay-agent-runs)).
- One mechanism brings an agent to that state, and both the daemon and the installer run it. The daemon runs it at startup whenever it runs the broker with exposure on, so a second instance gets a registered agent exactly as the installed one does. `install` runs it with exposure on, after the daemon has stopped and before it starts again.
- The mechanism restarts a running agent only when its executable or LaunchAgent changed or its broker moved, because the agent's open session keeps dialling the URL it began with. A new credential or authority alone is written into the configuration, which the running agent reads before its next dial ([RA-3](relay-agent.md#ra-3-the-relay-agent-dials-out)). An agent that runs as wanted is left alone.
- The instance trusts one Developer ID team to sign its agent (DC-231):
  - `MACHINE_SERVICE_RELAY_AGENT_TEAM_ID`, when set, is that team from the start.
  - Otherwise the team its record names: `<state>/relay/relay-agent-team.json`, mode 600 in a mode-700 folder, written atomically through a temporary file and a rename. The record holds the team, whether it came from the setting or the first installation, and when.
  - Before any record, the first Developer ID release that the mechanism installs is trusted, and its team, read from the executable's own signature, is recorded once the agent is in place. A configured team is recorded too, so removing the setting later keeps it. The daemon's own check of the release it holds records it the same way, for an instance with no durable agent to install (DC-237).
  - A release signed by any other team is refused, with the trusted team, the record's path and the fix: set the variable to the team you now trust, or remove the record. A release's `SIGNING.json` is never the trust anchor; it only has to agree with the executable. A record that cannot be read refuses every installation until it is fixed or removed, so a damaged record never trusts the next team anew. An ad hoc pre-release records nothing.
  - `/health` shows the trust as `relay_agent_team`: `{"fingerprint": "sha256:<16 hex digits of the SHA-256 of the team ID>", "origin": "configured" | "recorded"}`, `null` before any, never the team itself. The record lives in the state folder, never in the repository.
- The mechanism never replaces an agent signed with Developer ID by a build that is not (DC-232). It reads the installed executable's signature with `codesign` before anything is written, and refuses with the reason.
- `--rotate-relay-credential` makes a new credential; the restarted daemon accepts only it.
- With exposure off, `install` removes the installed instance's agent, and `remove` removes it with the service.
- A current durable lease refuses every restart of the relay agent, because a stopping relay agent ends the commands it runs (DC-118). The installer refuses to install; the daemon logs why and leaves the agent as it is.
- `machine-service-install relay-agent` installs the relay agent alone, for the instance that `MACHINE_SERVICE_STATE` and `MACHINE_SERVICE_SESSION_PORT` name, and `remove-relay-agent` removes it; neither touches machine-service's own LaunchAgent. There is no label to choose: the state folder names the agent.

## Tests

- AC-46 runs the built installer into an empty temporary folder and compares the result with `service_layout::required`: the same file names, each byte-equal to its build and mode `0755`, and nothing else. Removing any one executable from the build refuses the installation with nothing written. A Mac without Tart receives the core only.
- IN-1's own test resolves every helper path the daemon computes and checks that each names a file of the installation.
- The release tests install the release verbatim, refuse a tampered archive, a missing platform, an unsigned macOS executable, an ad hoc release that is not a pre-release, a `SIGNING.json` that disagrees with the executable, an invalid team setting and a missing release with nothing written, and remove the earlier layout's builds. The signature checks themselves are tested against recorded `codesign -dr -` output, and, with `RELAY_AGENT_TEST_IDENTITY`, against a real Developer ID signature.
- The trust tests (DC-231, DC-232): the first Developer ID team is accepted and recorded, mode 600, atomically; a release by another team is refused with the record's path and the setting; the configured team wins over the record and from the start; a damaged record refuses the installation with nothing written; an ad hoc pre-release records nothing; `/health` shows the fingerprint and never the team; an installed ad hoc agent may be replaced by an ad hoc pre-release. With `RELAY_AGENT_TEST_IDENTITY`, a throwaway executable signed with the keychain's Developer ID identity is trusted first, recorded, refused by another configured team, and never replaced by an ad hoc build.
- The daemon's trust tests (DC-236 to DC-241): `machine-service-core` checks the held release as the installer does (an ad hoc pre-release trusted and recording nothing; an ad hoc release, a foreign identifier and a damaged record refused) and, with `RELAY_AGENT_TEST_IDENTITY`, records the first team and refuses another with fingerprints only. At TL-2 the real daemon with the relay link and no durable exposure reports an untrusted release in `/health` and serves every lease over SSH without touching the guest; checks a release again before the next upload after it is replaced in place; never writes an untrusted release's build over a long-lived lease's agent; and never runs a `codesign` that the guest's `PATH` finds, the fake guest's `/usr/bin/codesign` standing in its `ssh`.
- IN-3's tests install the relay agent with exposure on and check its LaunchAgent, its executable against the release, its configuration and credential; keep the credential on reinstall and replace it on rotation; remove it with exposure off and on `remove`; refuse it during a durable lease and without a desktop session; and install a second instance's agent under the label and root its state folder names, with the operator's `HOME`, without touching machine-service's LaunchAgent or anything in the operator's home.
- A TL-2 test starts a second instance with exposure on and the relay link, and a `launchctl` that runs the LaunchAgents it loads: the daemon brings its own agent up, which registers and serves the lease, with every file under the state folder, and a restart of the instance leaves the running agent alone.
